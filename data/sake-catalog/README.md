# 都道府県順の日本酒追加SQL

初回確認：2026年11月10日。追加調査：2026年11月11日。商品ごとの確認日は出典台帳を参照してください。MySQL 8.0以降を対象とします。

既存の「一升の出会い」の `breweries`・`sake_types`・`sake` に、公式情報で名称・酒種・酒蔵所在地を確認した**個別商品**を追加します。新規作成用DDLではありません。登録済みのID・商品・酒蔵・会員・レビュー・診断タグを更新しません。

## ファイル

| ファイル | 用途 |
|---|---|
| `../sake_catalog_prefecture_order.sql` | 対象DBに適用する追加SQL |
| `import/sake_import_2296.sql.zip` | インポート用SQLの圧縮版。展開すると `sake_import_2296.sql` 1ファイル。検証済み2,296商品版と同一内容 |
| `regions/*.json` | 商品ごとの確認済み入力データ。追加調査分も同じ形式 |
| `sources.csv` | SQLの連番に対応する商品名・酒蔵・都道府県コード・酒種・公式出典・確認日 |
| `prefecture-counts.csv` | 01北海道〜47沖縄県の収録件数・酒蔵数。0件の県も表示 |
| `regions/41-47-exclusions.md` | 沖縄などの登録保留理由と公式出典 |
| `VALIDATION.md` | 2026年11月11日の検証結果・収録範囲・実DB未適用の記録 |

全商品を網羅した台帳ではなく、掲載ページで確認できた範囲の追加分です。公式サイト掲載は現在の在庫・通年販売・定価を保証しません。都道府県は確認した酒蔵所在地であり、全商品の瓶詰め・製造場所を個別に照合したものではありません。

過去の公式告知を根拠とする季節商品も一部含みます。告知年や季節販売終了を確認した商品は `source_note` に記録し、現在販売中という扱いにはしていません。

沖縄県は、泰石酒造の旧製品の現行供給を確認できず0件としました。県コード47までの確認結果は保留記録に残し、泡盛・焼酎などで埋めていません。

## 適用手順

### phpMyAdminでファイルをインポートする場合

1. [SQLファイル](../sake_catalog_prefecture_order.sql) を保存するか、[ZIP版](import/sake_import_2296.sql.zip) を保存して解凍します。
2. phpMyAdminの左側で、既存の「一升の出会い」の対象DBを選択します。
3. 「インポート」→「ファイルを選択」で `.sql` ファイルを選びます。形式はSQL、文字コードはUTF-8を指定して実行します。
4. 完了後の `status = completed`、追加件数・既存スキップ件数・保留一覧を確認します。

SQLはUTF-8・BOMなし、約613KBです。ZIP版の中身はSQLだけで、別ファイルの読込やSQL本文のコピーは不要です。既存テーブルにデータを追加する形式で、対象DBを作成・初期化するSQLではありません。MySQL 8.0以降を使用してください。ZIP版は2,296商品版の保存用であり、今後SQLを更新した場合は新しい版を使用してください。

### 接続先・実行時の確認

1. 接続先を確認して対象DBのバックアップを取得します。既定設定は `newbooze`、別環境では `issho_no_deai` などのため、名前を推測して実行しないでください。
2. `breweries`・`sake_types`・`sake` が既存DDLに沿って存在することを確認します。新規DBの場合は新規作成SQLによる準備が別途必要です。今回の追加のために既存DBを作り直す必要はありません。
3. 管理画面などでカタログへ登録する操作を止め、新しい専用接続でファイル全体を実行します。SQLには `USE` を含めず、指定したDBだけに適用します。
4. 出力される接続先、`status`、追加件数、県別の登録済みスキップ数・保留件数を確認します。`completed` でも酒蔵の衝突で保留になる商品があるため、保留一覧も確認してください。

MySQLクライアントの実行例（`接続先DB名`を実際のDB名へ変更）：

```bash
mysql --default-character-set=utf8mb4 --host=127.0.0.1 --user=登録権限のあるユーザー \
  --password 接続先DB名 < data/sake_catalog_prefecture_order.sql
```

パスワードはプロンプトで入力します。phpMyAdminの場合は対象DBを選び、SQLファイル全体をインポートします。`mysql --force` は使わず、途中エラーが出た場合は続行しないでください。接続が残っていれば `ROLLBACK;` を実行してから切断し、原因を確認してファイル全体を再実行します。途中からの再開はしません。

このチャットの作業環境にはアプリ用DBの接続設定がないため、適用先の実DBへは未適用です。検証用MySQLへの適用と、アプリの実DBへの適用を区別してください。

## 順番・重複・既存データ

- 追加商品の採番は、01北海道から46鹿児島県まで都道府県コード順です。県内は酒蔵名・商品名の照合キー順です。既存商品のID・並び順は変えません。47沖縄県は今回0件です。
- 容量・容器・箱・セットだけの違いは独立商品にしません。生／火入れ・原料・醸造仕様など、公式に別商品と確認できるものは区別します。
- 商品名の半角・全角空白、タブなどを取り除き、MySQLの `utf8mb4_unicode_ci` で照合します。全角英数字・半角カナ・大文字小文字の違いによる二重登録も防ぎます。公式名称の別名が分かる場合は入力JSONの任意項目 `aliases` に記録できます。名称が大きく異なる未登録の別名まで自動判定するものではありません。
- 現行スキーマは `sake.name` 単独UNIQUEです。同名商品は酒蔵や地域が違っても追加せず、既存行を保持します。初期10商品の総称と重なる商品は収集段階でも除外しています。
- 酒蔵名は空白・法人格の表記違いを照合します。既存酒蔵の県名が異なる場合や複数候補がある場合、その商品の登録を保留して一覧に出します。既存酒蔵の県名は更新しません。
- 酒種の「純米／純米酒」「吟醸／吟醸酒」などは同じ分類へ揃え、IDを参照します。商品・酒蔵・酒種のIDは固定しません。
- 同じSQLを再実行しても、登録済みの商品とマスタは増えません。DBごとの名前付きロックはこのSQLの並行実行を直列化します。管理画面等の書き込みを停止する機能ではありません。ロックを取得できなければ永続テーブルへの追加を行いません。

商品名・酒蔵・都道府県・酒種のみを追加し、未確認の度数・価格・紹介文・画像は `NULL` にしています。診断タグも推測していません。商品は検索・基本情報表示に使えますが、味わい診断への対応・説明文・写真・詳細ページ内の公式リンクは別途の確認と編集が必要です。今回の出典URLは台帳から参照できます。

## 追加調査と再生成

`regions` にJSON配列を追加します。必須項目は次のとおりです。

```json
{
  "prefecture_code": 1,
  "prefecture": "北海道",
  "brewery": "公式確認済みの酒蔵名",
  "name": "銘柄名を含む個別商品名",
  "sake_type": "純米大吟醸",
  "source_url": "https://公式サイトの商品またはカテゴリページ",
  "brewery_source_url": "https://公式サイトの所在地確認ページ",
  "checked_on": "2026-11-10",
  "source_note": "確認できた商品名・酒種・表記上の補記など"
}
```

`brewery_source_url` は商品ページ内で所在地も確認できる場合に省略できます。ブランドが一覧の共通見出しにある場合は商品名に補完し、その旨を `source_note` に残します。商品タイプを推測して入力しないでください。

リポジトリ直下で生成・照合します。Python標準ライブラリだけを使用します。

```bash
python3 scripts/build-sake-catalog.py
python3 scripts/build-sake-catalog.py --check
```

生成時に都道府県コード・県名・出典URL・日付・文字数・酒種・正規化後の商品名重複・別名重複を検査します。公式ページの再取得や商品情報の真偽判定は生成スクリプトの機能に含めません。調査者が公式情報を確認し、出典を入力してください。

## 検証

```bash
python3 scripts/tests/test_sake_catalog_mysql.py
```

ホストのアプリDBには接続せず、ポートを公開しない使い捨てMySQL 8.4コンテナ内で既存DDL・初期10商品を作成して検証します。Dockerと公式 `mysql:8.4` イメージが必要です。初回追加・再実行・既存値保持・県順・外部キー・表記違い・別名・酒蔵衝突を検証します。収録数の少ない旧版を適用した後に拡張版を実行する場合も、以前の商品ID・値・外部キーを保ったまま未登録商品だけが追加されることを確認します。

今回の変更はカタログ追加SQL・生成処理・台帳・検証に限定し、Java・画面・DB定義は変更していません。既存の要件定義・内部設計・DB設計と同名Word文書は仕様変更の対象外です。
