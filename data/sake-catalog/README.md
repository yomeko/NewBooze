# 都道府県順の日本酒追加SQL

初回確認：2026年11月10日。商品属性の追加・再確認：2026年11月11〜12日。商品・属性ごとの確認日は出典台帳を参照してください。MySQL 8.0とMariaDB 10.11を対象とします。

既存の「一升の出会い」に、公式情報で確認した**個別商品**を追加します。新規作成用DDLではありません。確認済みのアルコール度数・価格・画像URLも登録し、以前のSQLを取り込み済みの場合は空欄だけを補完します。既存のID・名前・酒蔵・酒種・会員・レビュー・診断タグや、入力済みの属性値は変更しません。

全商品を網羅した台帳ではなく、掲載ページで確認できた範囲の追加分です。公式サイト掲載は現在の在庫・通年販売・定価を保証しません。都道府県は確認した酒蔵所在地であり、全商品の瓶詰め・製造場所を個別に照合したものではありません。

過去の公式告知を根拠とする季節商品も一部含みます。告知年や季節販売終了を確認した商品は `source_note` に記録し、現在販売中という扱いにはしていません。

沖縄県は、泰石酒造の旧製品の現行供給を確認できず0件としました。県コード47までの確認結果は保留記録に残し、泡盛・焼酎などで埋めていません。

## 適用手順

### sakeを空にして作り直す場合

今回の再構築依頼には [再構築SQL](../sake_catalog_rebuild.sql) を使います。お気に入り・レビュー・商品タグ・詳細も初期化されます。通常の追加版とは目的が異なるため、先に [REBUILD.md](REBUILD.md) の削除範囲と手順を確認してください。再構築版はMariaDB 10.11専用です。

### phpMyAdminでファイルをインポートする場合

1. 初回登録は[全商品SQL](../sake_catalog_prefecture_order.sql)または[全商品ZIP](import/sake_import_2296.sql.zip)、以前の版を取り込み済みなら[属性補完SQL](../sake_catalog_attributes.sql)または[属性補完ZIP](import/sake_attributes_2296.sql.zip)を保存します。ZIPは解凍します。
2. phpMyAdminの左側で、既存の「一升の出会い」の対象DBを選択します。
3. 「インポート」→「ファイルを選択」で `.sql` ファイルを選びます。形式はSQL、文字コードはUTF-8を指定して実行します。
4. 完了後の `status = completed`、追加件数・既存スキップ件数・保留一覧を確認します。

SQLはUTF-8・BOMなしです。ZIP版の中身はSQLだけで、別ファイルの読込やSQL本文のコピーは不要です。対象DBを作成・初期化するSQLではありません。MySQL 8.0またはMariaDB 10.11を使用してください。ZIPも再生成・整合性検査の対象で、最新のSQLと同じ内容を含みます。

### MariaDBで不明な照合順序エラーが出た場合

旧版の `utf8mb4_ja_0900_as_cs_ks` はMySQL固有であり、MariaDB 10.11.19で `#1273` になることを確認しました。現在のSQLはその照合順序を使わず、文字幅とカナの濁点を一時キーで正規化した後、両DBにある `utf8mb4_bin` で属性の対応を判定します。濁点やアクセントが異なる別商品へ誤補完する単純な曖昧照合には置き換えていません。

旧版の属性インポートが失敗した場合は、最新の[属性補完SQL](../sake_catalog_attributes.sql)を保存し直して、同じ対象DBへインポートしてください。既存の商品ID・入力済み値は保持し、NULL/空文字だけを補完するため、最初の商品SQLをやり直す必要はありません。

### 接続先・実行時の確認

1. 接続先を確認して対象DBのバックアップを取得します。既定設定は `newbooze`、別環境では `issho_no_deai` などのため、名前を推測して実行しないでください。
2. `breweries`・`sake_types`・`sake`・`sake_page_details` が既存DDLに沿って存在することを確認します。古いDBに詳細テーブルがない場合は既存の `data/sake_page_details_schema.sql` を先に適用します。新規DBの準備は別途必要です。既存DBを作り直す必要はありません。
3. 管理画面などでカタログへ登録する操作を止め、新しい専用接続でファイル全体を実行します。SQLには `USE` を含めず、指定したDBだけに適用します。
4. 出力される接続先、`status`、追加件数・空欄補完件数・容量別価格の詳細登録件数・確認済み属性件数を確認します。`completed` でも同名や酒蔵の衝突で保留になる商品があるため、保留一覧も確認してください。属性専用版は既存行と一意に照合できない商品を一覧に出します。

MySQLクライアントの実行例（`接続先DB名`を実際のDB名へ変更）：

```bash
mysql --default-character-set=utf8mb4 --host=127.0.0.1 --user=登録権限のあるユーザー \
  --password 接続先DB名 < data/sake_catalog_prefecture_order.sql
```

パスワードはプロンプトで入力します。phpMyAdminの場合は対象DBを選び、SQLファイル全体をインポートします。`mysql --force` は使わず、途中エラーが出た場合は続行しないでください。接続が残っていれば `ROLLBACK;` を実行してから切断し、原因を確認してファイル全体を再実行します。途中からの再開はしません。

このチャットの作業環境にはアプリ用DBの接続設定がないため、適用先の実DBへは未適用です。検証用MySQLへの適用と、アプリの実DBへの適用を区別してください。

## 属性の内容と確認範囲

2,296商品のうち、数値の度数1,521件、税込価格919件、商品画像URL1,914件を収録しています。3項目が揃う商品は669件です。すべての商品・項目が確認済みという意味ではありません。

- 度数は公式の単一数値のみを `sake.abv` に登録します。「15〜16度」「15度以上16度未満」など196件は原文を出典台帳に残し、既存の小数カラムへ平均値や下限値を推測して入れません。
- 価格は公式に表示された税込の円価格です。720mlを優先し806件、720mlがない場合の113件は確認できた容量を使用します。税抜価格から税込価格を計算したり、容量別価格の最小値だけを採ったりしていません。箱なしと箱入りの同容量価格がある場合は箱なしを優先します。
- 容量は `attribute-sources.csv` に記録します。DB価格が確認済み価格と一致し、DB詳細がなく、同梱 `sake-pages.json` にIDがない商品には、`sake_page_details.detail_json` の `prices` に容量・税込価格を新規登録します。既存のDB詳細や同梱紹介文を隠す新規詳細は作りません。
- 画像URLは公式ページの当該商品写真と対応し、HTTPS・255文字以内・HTTP200・画像Content-Typeを確認した候補です。画像URLを登録しても公開利用の承認は行いません。公開画面は引き続き [商品写真の承認台帳](../PRODUCT_IMAGE_PUBLICATION.md) に従い、今回その台帳は変更していません。

以前の版を取り込み済みでも、属性補完版が `abv`・`price` のNULLと `image_url` のNULL/空文字だけを埋めます。既存の0や入力済みの値、画像URL、詳細JSONは上書きしません。公式仕様を確定できないもの、税込・容量の根拠がない価格、接続失敗や商品違いの画像はNULLにしています。

## 順番・重複・既存データ

- 追加商品の採番は、01北海道から46鹿児島県まで都道府県コード順です。県内は酒蔵名・商品名の照合キー順です。既存商品のID・並び順は変えません。47沖縄県は今回0件です。
- 容量・容器・箱・セットだけの違いは独立商品にしません。生／火入れ・原料・醸造仕様など、公式に別商品と確認できるものは区別します。
- 商品名の半角・全角空白、タブなどを取り除き、MySQLの `utf8mb4_unicode_ci` で照合します。全角英数字・半角カナ・大文字小文字の違いによる二重登録も防ぎます。公式名称の別名が分かる場合は入力JSONの任意項目 `aliases` に記録できます。名称が大きく異なる未登録の別名まで自動判定するものではありません。
- 現行スキーマは `sake.name` 単独UNIQUEです。同名商品は酒蔵や地域が違っても追加せず、既存行を保持します。初期10商品の総称と重なる商品は収集段階でも除外しています。
- 酒蔵名は空白・法人格の表記違いを照合します。既存酒蔵の県名が異なる場合や複数候補がある場合、その商品の登録を保留して一覧に出します。既存酒蔵の県名は更新しません。
- 酒種の「純米／純米酒」「吟醸／吟醸酒」などは同じ分類へ揃え、IDを参照します。商品・酒蔵・酒種のIDは固定しません。
- 同じSQLを再実行しても、登録済みの商品とマスタは増えません。DBごとの名前付きロックはこのSQLの並行実行を直列化します。管理画面等の書き込みを停止する機能ではありません。ロックを取得できなければ永続テーブルへの追加を行いません。
- 属性の補完は商品名/明示別名・酒蔵・都道府県が一意に対応する場合だけです。幅や英字大小の違いを許容しつつ、濁点・アクセント・ひらがな/カタカナが異なる別商品や別の酒蔵へ補完しません。

未確認の度数・価格・画像は `NULL` のままです。紹介文や診断タグは推測していません。味わい診断への対応・説明文・写真の公開利用は引き続き別途の確認と編集が必要です。

## 追加調査と再生成

`regions` にJSON配列を追加します。必須項目は次のとおりです。

```json
{
  "prefecture_code": 1,
  "prefecture": "北海道",
  "brewery": "公式確認済みの酒蔵名",
  "name": "銘柄名を含む個別商品名",
  "sake_type": "純米大吟醸",
  "source_url": "https://公式サイトの商品またはカテゴリページ",
  "brewery_source_url": "https://公式サイトの所在地確認ページ",
  "checked_on": "2026-11-10",
  "source_note": "確認できた商品名・酒種・表記上の補記など"
}
```

`brewery_source_url` は商品ページ内で所在地も確認できる場合に省略できます。ブランドが一覧の共通見出しにある場合は商品名に補完し、その旨を `source_note` に残します。商品タイプを推測して入力しないでください。

リポジトリ直下で生成・照合します。Python標準ライブラリだけを使用します。

```bash
python3 scripts/build-sake-catalog.py
python3 scripts/build-sake-catalog.py --check
```

生成時に都道府県コード・県名・出典URL・日付・文字数・酒種・正規化後の商品名重複・別名重複を検査します。通常版・属性版に加えて再構築版と各ZIPも出力します。生成コマンドはDBへSQLを実行しません。公式ページの再取得や商品情報の真偽判定は生成スクリプトの機能に含めません。調査者が公式情報を確認し、出典を入力してください。

属性は `enrichment/*.json` の配列に、既存の商品名・都道府県コード・酒蔵名で対応させます。各値の出典URL・確認日が必要です。価格には `volume_ml` と `price_tax_included: true`、画像にはHTTP200と `image_content_type` の確認を記録します。画像だけ後日に再確認した場合は `image_checked_on` に日付を残します。形式と禁止条件は生成スクリプトの `apply_enrichment` で検査し、商品不一致・属性重複・不正なURL・範囲を単一数値にした度数・容量税区分不明の価格・代替画像を拒否します。

## 検証

```bash
python3 scripts/tests/test_sake_catalog_mysql.py
python3 scripts/tests/test_sake_catalog_mysql.py --image mariadb:10.11
```

ホストのアプリDBには接続せず、ポートを公開しない使い捨てコンテナ内で既存DDL・初期10商品を作成して検証します。Dockerと公式 `mysql:8.4`・`mariadb:10.11` イメージを使用します。初回追加・再実行・既存値保持・県順・外部キー・表記違い・別名・酒蔵衝突に加え、以前の空欄版からの属性補完、手入力値と紹介文の保持、誤商品への補完拒否を両DBで確認します。半角カナの濁点・半濁点・結合文字、混在幅の法人格も境界テストに含みます。

今回の変更はカタログ追加SQL・生成処理・台帳・検証に限定し、Java・画面・DB定義は変更していません。既存の要件定義・内部設計・DB設計と同名Word文書は仕様変更の対象外です。
