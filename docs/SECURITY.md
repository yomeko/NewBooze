# 公開前の安全対策と運用手順

更新日：2026-10-21

この文書は安全対策の実装仕様と、既存データを保持して公開準備するための手順です。チェック欄は実施記録用です。文書・SQLの追加だけで、実DBへの適用、実メールでの再設定、公開HTTPS環境の確認が完了したとは扱いません。過去のメール認証検証は [email-verification.md](email-verification.md) の日付付き記録を参照してください。

## 実装した対策

| 対象 | 動作 |
|---|---|
| 初期管理者 | 作成は既定で無効。明示的な初回設定だけで作成し、既存会員の上書き・昇格をしない |
| 旧管理者 | 旧既定パスワードの管理者をログイン・セッションの両方で拒否。既存レコードは自動変更しない |
| パスワード再設定 | 認証済み会員にだけ30分・一度限りのリンクを送り、要求時点では旧パスワードを維持する |
| 再設定の秘密 | 32バイト乱数のURL-safeトークンを発行し、DBはSHA-256の64文字ハッシュ・期限・送信日時だけを保持 |
| 再設定の確定 | GETでトークンをセッションへ移してURLから除き、新パスワード・確認入力とCSRF保護付きPOSTで確定。自動ログインしない |
| 再設定リンクの失効 | 再送成功・使用成功・パスワード変更・メールアドレス変更で旧ハッシュと期限を失効。60秒間隔のため送信日時は維持 |
| 再設定の送信 | 会員ごと60秒以上の間隔。未登録・未認証・間隔未満・SMTP失敗にも共通受付案内。SMTP失敗時はDB更新を戻す |
| 古いログイン状態 | 静的ファイルを除く認証済みリクエストでDB照合。会員削除、ハッシュ・メール・認証状態・権限の変更時に失効 |
| プロフィール画像 | 実形式がJPEG・PNG・GIFで2000万画素以下か展開前に確認。GIFの論理画面・後続フレームも検証し、不正画像は保存しない |

再設定画面はno-storeとno-referrerを返します。メール内リンクはリクエストのHostではなく固定の `APP_BASE_URL` から作成し、公開用はHTTPS、開発用はlocalhostのHTTPを使います。最初のリンクのURLにはトークンが含まれるため、アクセスログ・解析・エラー記録でもクエリの秘密値を残さない設定を確認してください。

画像の受信上限は20MB、保存上限は900KBです。大きい画像は長辺1600px以下を初期目標にJPEGへ圧縮し、小さいGIFは元のバイト列を保存してアニメーションを維持します。画像の変更時は表示位置・拡大率を中央・等倍へ戻します。

## 連続操作の制限

CSRF検証後の次のPOSTを、認証・メール送信より前に制限します。異なるURLの上限は別に数え、ログインはIPとログインIDの両方の条件を満たす必要があります。

| 操作 | URL | 制限 |
|---|---|---|
| ログイン | /login | IPごと20回／5分、ログインIDごと10回／5分 |
| 会員登録 | /signup | IPごと5回／15分 |
| 再設定メール要求 | /forgot-password | IPごと5回／15分 |
| 新パスワードの確定 | /reset-password | IPごと10回／15分 |
| 認証メール再送 | /verify-email/resend | IPごと10回／15分 |
| メール認証確定 | /verify-email | IPごと20回／15分 |

超過時はHTTP 429と `Retry-After` を返します。許可した要求を数え、制限中の要求によって待ち時間を延ばしません。管理キーはSHA-256で保持し、IP・ログインIDの原文は保存しません。最大20000件をプロセス内メモリーで管理し、満杯時は有効な記録を追い出さず新しい要求を待たせます。

この記録はアプリ再起動で消えます。複数インスタンスでは各アプリの上限が独立するため、公開構成に合わせて共有の制限機構を用意する必要があります。これはSMTP事業者の送信上限を代わりに管理する機能ではありません。

## 既存DBの移行

- [ ] 実際の接続URL、DB名、設定の上書きを確認する。既定の `newbooze` とローカル設定の別DBを混同しない。
- [ ] 対象DBのバックアップと復元手順を用意し、バックアップをGit管理外・適切なアクセス制限下に置く。
- [ ] `users` の既存列・索引を確認する。メール認証の4列が未追加なら `data/email_verification_schema.sql` を先に適用する。
- [ ] 再設定の3列・索引が未追加のDBへ、停止または利用を制限した状態で `data/password_reset_token_schema.sql` を一度だけ適用する。SQLには `USE` がないため対象DBを明示して実行する。
- [ ] `password_reset_hash VARCHAR(64) NULL`、`password_reset_expires_at DATETIME NULL`、`password_reset_sent_at DATETIME NULL` と一意索引 `uk_users_password_reset_hash` を確認する。
- [ ] 既存会員・パスワード・権限・関連レコードが保持されていることを確認する。新規作成SQLを既存DBへ実行したり、`reset_newbooze.sql` で初期化したりしない。
- [ ] `spring.jpa.hibernate.ddl-auto=validate` のまま起動し、構造の検証を確認する。

新規作成SQLには同じ再設定列・索引を含むため、新規作成後に差分を重複適用しません。旧 `data/password_reset_schema.sql` は旧方式の `temporary_password` 列用であり、新しい差分の代わりにはなりません。旧フラグは互換性のため残し、今回から仮パスワードを新規発行しません。

## 管理者の移行

- [ ] 外部からのアクセスを制限した初回設定環境を用意し、既存管理者と関連レコードを確認する。
- [ ] 既存会員と重複しない管理者用のメールアドレスを決め、十分な強度の新しいパスワードを生成する。
- [ ] 初回だけ `ADMIN_BOOTSTRAP_ENABLED=true`、`ADMIN_EMAIL`、`ADMIN_PASSWORD`、必要な `ADMIN_NAME` を安全な設定先へ登録する。
- [ ] 新しい管理者が作成され、その認証情報で `/admin` を利用できることを確認する。同じメールが存在する場合は上書き・昇格されないため、別の一意のアドレスを使う。
- [ ] `ADMIN_BOOTSTRAP_ENABLED=false` に戻し、初回用パスワードの設定を除いて再起動する。
- [ ] 旧管理者の扱いを明示的に決める。レコードを保持しながら旧権限を解除する場合も、一般会員として旧パスワードが利用可能にならないよう認証情報を更新する。関連データの一括削除で対処しない。
- [ ] 旧既定パスワードでのログインと、古い管理者セッションでの操作が拒否されることを確認する。

初回パスワードは12文字以上・UTF-8で72バイト以内、英大文字・英小文字・数字・記号から3種類以上を使用し、既知の単純な値や短い繰り返しを避けます。環境変数の詳細は [admin.md](admin.md) を参照してください。秘密値をコマンド履歴・チャット・コミットへ残しません。

## 公開構成で残る確認

- [ ] 公開URLと `APP_BASE_URL` をHTTPSで一致させ、DB・SMTPの認証情報を安全な設定先から渡す。
- [ ] プロキシ・アプリ間のアクセス範囲を制限し、外部からアプリへ直接到達して制限を回避できないことを確認する。
- [ ] 信頼するプロキシを限定して利用者IPを取得する方法を決める。現行処理は `getRemoteAddr()` を使い、`X-Forwarded-For` 等を直接読み取らない。単一プロキシのIPが全利用者のIPになるままでは、正当な利用者も同じ制限を共有する。
- [ ] 転送ヘッダーを利用者が自由に指定してIPやHTTPS判定を偽装できないことを確認する。ヘッダーを無条件に信用する設定だけで解決しない。
- [ ] HTTPS下のCookie、ログアウト、CSRF、セッション失効、キャッシュ・参照元ヘッダーを実際の公開経路で確認する。
- [ ] 複数インスタンスの場合は回数制限の共有方式を用意し、再起動や別インスタンスで簡単に上限を回避できないことを確認する。
- [ ] DBと画像の保存先・バックアップ・復元を公開環境で確認する。
- [ ] アクセスログ・障害ログ・監視へ再設定トークン、認証トークン、パスワード、SMTP認証情報を出さない。

信頼するプロキシと利用者IPの取り扱い、実HTTPSでの動作確認は公開先を決めてから行う作業です。この文書では完了としていません。

## 変更後の動作確認

- [ ] 再設定メール要求だけでは旧パスワードでのログインが維持される。
- [ ] 未認証会員には送信せず、未登録・送信間隔未満・SMTP失敗でも共通受付案内となる。
- [ ] メールリンクのGETと自動検査ではパスワードを変更せず、画面表示時にURLからトークンが除かれる。
- [ ] 新パスワードの確定はCSRFと確認入力を要求し、期限切れ・使用済み・再送前のリンクを拒否する。
- [ ] パスワード・メールアドレス変更で未使用の再設定リンクが失効し、別ブラウザの古いセッションも拒否される。
- [ ] 各回数上限とHTTP 429・Retry-After、管理者の権限変更・削除時のセッション失効を確認する。
- [ ] 過大な画像ヘッダー・GIFの巨大な描画領域・壊れた画像を拒否し、正常画像の圧縮・表示調整が維持される。

実行結果はコマンド、対象環境、実施日、未確認範囲を分けて記録します。JUnit・ブラウザ・実DB・実メール・公開環境の確認を混同しません。
