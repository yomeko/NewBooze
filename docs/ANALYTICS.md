# 人気・閲覧数の集計

コード・DDLの仕様更新日：2026-11-18。公開サーバーでの計測確認を示す日付ではありません。

## 管理トップで確認できる内容

`/admin` は管理者権限を持つ会員だけが開けます。公式サイトへの累計遷移数、サイトの累計閲覧数（PV）と当日のPV、直近14日間のPVを横棒グラフで表示します。公式サイトへの遷移数を基準に、銘柄全体の上位10件、タグ別の累計件数、タグごとの銘柄上位5件も確認できます。

順位は件数の降順、同数なら銘柄IDの昇順です。タグ別件数は件数の降順、同数ならタグIDの昇順です。未計測のタグも0件で表示し、遷移がない銘柄はランキングに入りません。上位件数に満たない場合は実際に計測された銘柄だけを表示します。

## 公式サイトへの遷移

商品詳細の公式リンクはアプリ内の次のURLを経由します。遷移先は登録済みの商品紹介情報からサーバー側で決定します。利用者が任意の転送先URLを指定する方式ではありません。

| URL | 遷移先 |
|---|---|
| `GET /sake/{id}/outbound/official` | 登録済みの公式サイトURL |
| `GET /sake/{id}/outbound/purchase` | 最初の公式購入先。未登録なら公式サイトURL |

1回の遷移で銘柄に1件、その時点の `sake_tags.score > 0` の各タグに1件ずつ加算します。例えば「辛口」「軽快」がある銘柄を開いた場合、銘柄は1件、辛口は1件、軽快は1件です。重みが3のタグも1のタグも、遷移数には1件として扱います。したがって、タグ別件数の合計が銘柄の総遷移数を上回る場合があります。

銘柄とタグの組み合わせごとに計測時の件数を保存するため、後日タグの対応・重みを変更しても過去の件数を新しいタグへ付け替えません。タグ別トップ5もこの計測時の対応を使います。タグがない銘柄では銘柄だけを加算します。再度リンクを開くと再度加算するため、人数や購入完了数を表す指標ではありません。

## 閲覧数（PV）

対象ページのHTML表示に成功したGETを1PVとして、日付とページパスごとに加算します。再表示も1PVです。日本時間（`Asia/Tokyo`）で日付を区切り、当日を含む直近14日間を表示します。閲覧がない日も0件として表示し、その期間で最も多い日の棒を最大幅にします。累計PVには14日より前の件数も含みます。

対象は次のページパスです。商品詳細は存在する正のIDのURLだけを対象にします。検索・レビューの並べ替えや診断結果のIDなどのクエリ文字列は保存しません。

| 区分 | 対象パス |
|---|---|
| 銘柄を探す | `/`、`/search`、`/sake/{id}`、`/brewery-map`、`/categories`、`/tags` |
| ガイド・公開案内 | `/guide`、`/about`、`/privacy`、`/external-transmission`、`/contact` |
| 診断 | `/diagnosis`、`/diagnosis/result` |
| 会員向け | `/ranking`、`/pairings`、`/goods`、`/posts`、`/mypage`、`/mypage/account`、`/mypage/diagnosis-history` |

管理画面、認証用画面、静的ファイル、エラー、転送、HEAD、POSTはPVの対象から除きます。`PageViewAnalyticsConfig.PageViewInterceptor` はControllerがHTMLを表示し、描画完了時に例外がなくHTTP 200・`text/html`を返した場合にだけ加算します。JavaScriptや外部のアクセス解析サービスは使いません。

PVと公式リンクのどちらも `AnalyticsRequestPolicy` で先読み・明示的な自動巡回を除きます。`Purpose`、`Sec-Purpose`、`X-Purpose`、`X-Moz` ヘッダーに `prefetch` または `prerender` がある要求と、User-Agentに `bot`、`spider`、`crawler`、`slurp`、`headless` がある要求を除外します。判定時は大文字・小文字を区別しません。User-AgentがないGETは対象となり、識別できない自動巡回まで完全に除く仕組みではありません。

記録するのは銘柄ID・タグID・日付・対象ページパスと件数です。IPアドレス、会員ID、メールアドレス、User-Agent、検索語や認証トークンを含むクエリ文字列を集計テーブルに保存しません。集計値は管理画面でのみ表示します。

## 保存方式

| テーブル | 保存する集計 |
|---|---|
| `analytics_sake_clicks` | 銘柄ごとの公式サイト遷移数 |
| `analytics_tag_clicks` | タグと銘柄の組み合わせごとの遷移数 |
| `analytics_page_views` | 日本時間の日付とページパスごとのPV |

MySQL／MariaDBの加算付きupsertで保存し、複数アクセスが重なっても読取後の上書きによって件数を失わないようにします。銘柄件数と各タグ件数は同じトランザクションに含めます。アプリのメモリだけに保存しないため、再起動してもDBの集計を引き継ぎます。マスタの削除時に関連集計も削除される点には注意が必要です。通常のタグの付け替えでは集計行は削除しません。

DBアクセス・トランザクションの障害（`DataAccessException` または `TransactionException`）は、集計処理の外側で処理します。公式リンクは登録済みサイトへの転送を続け、PVの障害は表示済みページの利用を妨げません。管理トップで集計を読めない場合は取得失敗の案内を表示し、0件だったと誤表示しません。障害の種類をログへ記録しますが、URLのクエリや利用者の入力値はログへ出しません。障害中の件数を後から自動復元する処理はありません。

## 既存DBへの適用

1. 実際の起動方法、環境変数、Git管理外の `application-local.properties` から接続先DBを確認します。既定名が `issho_no_deai` でも、必ず実際の接続先を確認します。認証情報をログへ出しません。
2. 対象DBをバックアップし、そのDBを指定した接続で `SELECT DATABASE()` を確認します。
3. アプリ更新前に [analytics_schema.sql](../data/analytics_schema.sql) を適用します。このSQLは `USE`、既存行の削除、既存テーブルの初期化を含まず、集計用3テーブルを `CREATE TABLE IF NOT EXISTS` で追加します。
4. 3テーブルの定義と外部キーを確認してからアプリを起動します。`ddl-auto=validate` は維持します。集計テーブルはJdbcTemplateで使うため、JPAの検証だけを適用確認の代わりにしません。
5. 公開予定のDBで、対象ページを開いた後にPVが増えること、公式リンクを開いた後に銘柄と各タグが増えること、管理トップ自身の閲覧でPVが増えないことを確認します。

新規DB向けの [create_issho_no_deai.sql](../data/create_issho_no_deai.sql) にも同じ3テーブルを含めます。既存DBに新規作成SQLやリセットSQLを実行して移行しません。計測開始前の過去の遷移数・PVを復元する処理はありません。

## 検証

`AnalyticsIntegrationTests` は実DB上にテスト専用の銘柄・タグ・集計を用意し、終了時にトランザクションをロールバックします。タグの重みによらず1件ずつ数えること、タグ変更後の過去集計、順位の上限と同点順、日別PVの集計を確認します。転送先・除外条件・管理者権限は関連するControllerとInterceptorのテストで確認します。実行結果とブラウザ確認は作業完了報告に記載します。
