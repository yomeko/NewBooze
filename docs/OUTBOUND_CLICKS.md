# 公式サイトへのクリック数

仕様・コード・DDL更新日：2026年11月12日。適用・検証の実施結果は、その環境と実施日を分けて記録します。

## 目的と数え方

「一升の出会い」から公式の商品情報や購入先へ進むきっかけを作れた回数を確認します。会員登録・ログインの有無に関係なく、対象のボタンを1回押す操作を1件として保存します。同じ人が2回押した場合は2件です。人数、公式サイトの表示完了、購入・申込みの件数を表すものではありません。過去の直接リンクによる移動は後から集計できず、導入後の操作が対象です。

| 画面 | 対象 |
|---|---|
| 商品詳細 | 「購入先を見る」「もっと詳しく：酒造の公式サイト」 |
| ホーム | 編集者が選ぶメジャー銘柄の公式商品情報・公式購入先案内 |
| 初心者ガイド | 2つの公式取扱店案内と、保存方法・商品・FAQの公式出典 |

同じURLが複数の場所に登場しても、それぞれを開く操作を1件ずつ数えます。ページの表示、通常のGET、ブラウザの先読みだけでは加算しません。

ログイン中は認証情報のアカウントIDを保存します。未登録・未ログイン時はアカウントIDを保存しません。登録済みでもログインしていなければアカウント別には紐付きません。計測用の識別Cookie・IPアドレス・User-Agentを追加保存せず、既存のセッションCookieとCSRF保護を使います。

## 記録と画面遷移

対象の導線は標準のPOSTフォームで、CSRFトークンを含めて `/sake/outbound` に送信します。新しいタブで開き、noopener・noreferrerを指定します。JavaScriptなしでも操作できます。Serviceが既存の設定データから移動先を解決し、Repositoryが1件を保存した後、303で公式サイトへ転送します。アカウントIDや任意の移動先URLをリクエストの値から採用しません。

| source | target | kind | 移動先の解決元 |
|---|---|---|---|
| detail | カタログの銘柄ID | official | SakePageServiceの公式URL。DB保存済み紹介を優先 |
| detail | カタログの銘柄ID | purchase | 最初の公式購入先。なければ公式URL |
| home | メジャー候補の名称 | product / retailer | SakeDiscoveryServiceのmajorReferences |
| guide | dassai / dewazakura | retailer | ガイド掲載済みの公式取扱店URL |
| guide | japansake / houraisen / dassai-faq | reference | ガイド掲載済みの保存方法・商品・FAQの出典URL |

存在しない対象、不正な種類・組合せ、URL未登録は404とし、記録・転送を行いません。CSRFなしのPOSTは403です。保存に失敗した場合は成功扱いせず、日本語の説明と戻り先を表示します。

`outbound_clicks` にはクリック時点の対象名・移動先・導線・日時を保存します。日時はアプリ側でAsia/TokyoのLocalDateTimeを指定し、管理画面にも日本時間と表示します。DBサーバーやJVMの既定タイムゾーンに依存させず、取得時もLocalDateTimeで扱います。アカウント削除時は `user_id`、銘柄削除時は `sake_id` を外部キーのSET NULLで匿名化・解除し、合計を保持します。`logged_in` に操作当時の認証状態を残すため、退会によって未ログイン・ログイン中の内訳は変わりません。カラム定義は [DB_DESIGN.md](DB_DESIGN.md) 第4.20節を参照してください。

## 管理画面

ADMIN限定の `/admin/outbound-clicks` で次を確認します。未ログイン利用者はログイン画面へ案内し、一般会員からの閲覧を拒否します。

- 全クリック数と、未ログイン・ログイン中の内訳。
- 現在存在するアカウントごとの件数・最終クリック日時。30件ずつ表示。

管理者自身のクリックも数えます。退会済みアカウントのクリックは全体・ログイン中の合計に残りますが、アカウント別一覧には表示しません。このため、アカウント別の合計がログイン中の合計より少ない場合があります。記録がなければ0件と案内します。アカウントのメールアドレスはこの集計画面に表示しません。

## 既存DBへの適用

1. `application.properties`、Git管理外の `application-local.properties`、環境変数・起動引数を確認し、実際の接続先DBを確定します。既定の `newbooze` と、過去のローカル記録の `issho_no_deai` を取り違えないでください。認証情報をログやGitへ残さず、既存のデータと定義をバックアップします。
2. 選択した接続で `SELECT DATABASE(), @@session.time_zone, @@global.time_zone;` を実行して対象を確認します。表示する日時とAsia/Tokyoの整合を確認してください。`SHOW TABLES LIKE 'outbound_clicks';` で追加済みか調べます。
3. 同じ接続先へ [outbound_clicks_schema.sql](../data/outbound_clicks_schema.sql) を実行します。このSQLはDBを選択するUSEを含まず、CREATE TABLE IF NOT EXISTSで新テーブルを追加します。既存の会員・商品・記録の削除や初期化は行いません。同名テーブルが既にある場合は、CREATEだけで既存定義を変更しない点に注意してください。
4. `SHOW CREATE TABLE outbound_clicks;` で列・索引・users/sakeへのSET NULL外部キーを照合します。JDBC専用テーブルのため、JPAの `ddl-auto=validate` だけではこのテーブルを検証できません。`ddl-auto=validate` と `open-in-view=false` は維持します。
5. アプリを起動して、匿名・ログイン中のクリックと管理集計を確認します。検証によるクリックも1件として残るため、本番の成果と混在させないよう、独立した検証環境を使ってください。

新規DB用の [create_issho_no_deai.sql](../data/create_issho_no_deai.sql) にも同じテーブルを含めます。新規作成SQL全体を既存DBに再適用したり、`reset_newbooze.sql` を実行したりする必要はありません。
